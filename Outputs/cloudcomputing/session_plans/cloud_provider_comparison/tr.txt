Slide 1: Five Providers in the Cloud Landscape
Heading: Cloud Provider Landscape
Subheading: Five Key Players

Content:

        A cloud provider is a company that offers computing resources such as servers,
        storage, databases and networking over the internet, on a pay-as-you-go basis.
        AWS, Azure and Google Cloud lead the market, while IBM Cloud and Oracle
        Cloud serve specific enterprise needs.

●​ Amazon Web Services (AWS), Microsoft Azure (Azure), Google Cloud (GCP): the three
   hyperscalers
●​ IBM Cloud: enterprise and hybrid-cloud focused provider
●​ Oracle Cloud Infrastructure (OCI): database and enterprise-application focused provider
●​ Market position ranges from broad general-purpose platforms to niche enterprise
   specialists

Visual Guidance: Five logo boxes sized by relative market position: AWS largest, Azure and
GCP mid-sized, IBM Cloud and OCI smaller specialist boxes.

Speaker Notes: "Name all five providers together before going into any one of them. Point
out that size in the diagram reflects market position, not technical capability. Interviewers
often ask for all five by name, not just the top three."

Slide 3: IBM Cloud and Oracle Cloud Explained
Heading: IBM And Oracle Cloud

Subheading: Enterprise Specialists

Content:

Some organisations need a provider built around decades of existing enterprise systems
rather than service breadth; IBM Cloud and Oracle Cloud Infrastructure (OCI) serve exactly
that need.

●​ IBM Cloud: hybrid cloud and mainframe migration for regulated industries
●​ OCI: built around Oracle database and ERP workloads, and now a major provider of
   large-scale AI/GPU infrastructure
●​ Chosen for existing vendor relationships rather than broad service catalogs

Note : Five-provider comparison is covered in the post-session reading material.



Analogy: A general physician treats most common ailments, but a patient with a specific
heart condition goes to a cardiologist — just as IBM Cloud and Oracle Cloud specialise in
enterprise and database workloads rather than general-purpose breadth.

Visual Guidance: Two-column diagram: generalist hyperscalers on the left, specialist
enterprise providers (IBM Cloud, OCI) on the right, with an arrow showing narrower focus.

Speaker Notes: "Explain that lower market share does not mean lower capability, only a
narrower target customer. A bank already running mainframes is the classic IBM Cloud
example to mention aloud. Expect an interview question on why a company would ever pick
a smaller provider."

Slide 6: Four Service Categories Across Providers
Heading: Four Service Categories

Subheading: Same Capability Renamed

Content:

Every provider sells the same four building blocks — a virtual machine, object storage, a
managed database and a network boundary — under its own product name.

●​   Compute: rentable virtual machines for running applications
●​   Storage: object storage for files accessed by key
●​   Database: managed relational and NoSQL engines
●​   Networking: an isolated virtual network plus traffic distribution

Visual Guidance: Four-row map on screen: Compute, Storage, Database, Networking, each
with one AWS icon, one Azure icon, one GCP icon beside it.
Speaker Notes: "Set up the pattern before naming any product: the capability is identical,
only the label changes. Ask: why would a company moving from one provider to another
need a naming map rather than a new architecture?"



Slide 7: Why The Same Service Has Three Names
Heading: Service Equivalence Idea

Subheading: Translating The Label

Content:

When a capability already known on one provider exists on another under a different brand
name, that matching is called a service equivalent — the core function is the same, though
features and details can differ.

●​ Core capability and typical use case stay the same
●​ Learning one provider’s services makes the others much faster to learn

Analogy: Three telecom companies sell the same prepaid data-and-calls recharge under
three different plan names — just as three cloud providers sell the same virtual machine
capability under three different product names.

Visual Guidance: Single slide: one grey box labelled 'capability' with three coloured arrows
pointing to AWS, Azure, GCP product name tags.

Speaker Notes: "Say the everyday version first — same plan, different brand — before
naming it 'service equivalence'. Point out this is exactly the skill an interviewer tests when
asking to map an AWS service to its Azure or GCP counterpart."

Slide 13: Managed ML Platforms Beyond Pre-Built APIs
Heading: Managed ML Platforms

Subheading: Beyond Pre-Built APIs

Content:

Pre-trained AI APIs handle only fixed tasks. A managed Machine Learning (ML) platform
gives one workspace to build, train and deploy your own model without managing servers..

●​   Built-in notebooks and GPU-backed training environments
●​   Experiment tracking records accuracy across training runs
●​   One-click hosting turns a trained model into an endpoint
●​   AutoML cuts the coding needed to reach a trained model

Analogy: A ready-made shirt off the rack is a pre-built AI API; a tailor who takes
measurements and stitches to order is the managed ML platform — just as the tailor needs
fabric, measurements and time, the platform needs data, training and tuning before it
delivers a custom model.

Visual Guidance: Two boxes side by side: 'Pre-built API: input to output' versus 'ML
platform: data to train to tune to deploy', connected by arrows.

Speaker Notes: "Contrast calling Amazon Comprehend with building a custom fraud model
from the organisation's own data. Mention AWS SageMaker Studio as the console where this
workspace lives. Interview hook: ask when a pre-built API is insufficient for a use case."

Slide 16: Choosing Platform or API
Heading: Platform Vs API

Subheading: Choosing The Service

Content:

The two layers answer different needs: a ready model for a standard task, or a workspace to
build one that is genuinely custom.

●​ Pre-built API fits when the task matches an existing model
●​ Full platform fits when training is needed on private data
●​ AutoML sits between the two, inside the platform console


Visual Guidance: Simple two-box decision flow: 'standard task' arrow to pre-built API box,

Speaker Notes: "Close by framing the choice as standard task versus custom data, not as

console walkthrough coming next. Exam hook: ask when AutoML is the right middle choice."

Slide 17: One Task, Three Consoles
Heading: Same Task Three Ways

Subheading: Console Entry Points

Content:

Launching a compute instance follows the same decisions on every provider; each console
simply places them on a different screen, with the AWS console as the familiar reference
point.

●​   AWS Console: EC2 dashboard, Launch Instance wizard
●​   Azure Portal: Create a resource, Virtual Machine blade
●​   GCP Console: Compute Engine, VM instances page
●​   GCP Cloud Shell: browser-based command-line alternative
Visual Guidance: Three browser windows side by side: AWS EC2 console, Azure Portal, GCP
Console — same 'Create VM' action highlighted in each.

Speaker Notes: "Open the actual AWS EC2 console live and name the launch wizard as the
reference point. Mention that Azure and GCP will perform the identical task next."



Slide 18: AWS Launch Wizard Walkthrough
Heading: AWS Launch Wizard

Subheading: EC2 Decision Flow

Content:

The EC2 launch wizard, reached from the EC2 dashboard's Launch Instance button, lines up
every provisioning decision in one linear screen.

●​   Name and tags: identifies the instance for billing and search
●​   Amazon Machine Image (AMI): picks the pre-configured operating system
●​   Instance type: sets vCPU and memory for the workload
●​   Key pair: sets the credential used for SSH login
●​   Network and security group: places the instance and opens ports
●​   Launch: confirms the choices and starts provisioning

Visual Guidance: Screen capture of the EC2 Launch Instance wizard with each of the six
sections numbered 1 to 6 down the page.

Speaker Notes: "Walk the live EC2 console top to bottom, pointing at each wizard section as
it is named. Ask: which field here decides the operating system versus the one that decides
sizing?"

--------------------------------------- SECTION 5: 5. Choosing a Provider: What
genuinely differs (pricing, regions, service maturity, skills) vs what's cosmetic
(naming, console layout) ---------------------------------------

Slide 21: Real vs Cosmetic Differences
Heading: Choosing A Provider

Subheading: Real Vs Cosmetic

Content:

Picking among AWS, Azure and GCP is not a matter of which console looks friendlier; a small
set of factors actually changes cost or capability, while many more only change labels on
screen.

Category                                           What It Covers
Decision-changing                                  Pricing model, region footprint, service
                                                   maturity, team skills
Cosmetic only                                      Service names, console menu layout,
                                                   dashboard arrangement
Visual Guidance: Two-column split screen: left labelled 'Changes the outcome', right
labelled 'Just a different label' with icons for each factor.

Speaker Notes: "Frame the whole section as a filter: ask of every difference, does it move
cost or capability, or only the screen. Point out that this filter is what an interviewer is really
testing when they ask 'why AWS over Azure'."
Slide 22: Factors That Actually Decide
Heading: Real Differentiators

Subheading: Price Region Skill

Content:

Each factor below changes total spend, latency guarantees or hiring effort, which is why it
belongs in a provider decision rather than a preference.

●​ Pricing: on-demand rates, discount tiers and data-egress fees vary by provider
●​ Regions: footprint differs by provider; Azure lists the most regions, while AWS builds
   every region with at least three availability zones
●​ Maturity: a newer provider service may lack features an older one already shipped
●​ Skills: certification pools and job-market depth differ sharply across the three
●​ Checked in practice on the AWS Pricing Calculator and the AWS Regions page

Visual Guidance: Four labelled pillars (Pricing, Regions, Maturity, Skills) under one heading
'Decision Factors', each with a one-icon cue.

Speaker Notes: "Explain that region count affects latency and data-residency compliance,
not just marketing. Mention that service maturity means checking whether a needed feature
is generally available or still in preview. Interview angle: ask why egress cost alone can flip a
multi-cloud decision."



Slide 23: Cosmetic Differences and Checklist
Heading: Cosmetic Surface

Subheading: Naming And Layout

Content:

The same underlying service appears under a different name and menu path on each
console; this changes nothing about cost or capability.

●​ EC2, Virtual Machines, Compute Engine: one compute concept, three labels
●​ Console menu order and dashboard layout differ with no effect on behaviour
●​ Switching this surface costs only relearning time, not architecture or budget

A provider choice is settled by pricing fit, region coverage, service maturity and team skill;
Naming and layout build familiarity, but they are not criteria for choosing a provider.

Visual Guidance: Side-by-side console screenshots style icons for AWS, Azure, GCP showing
the identical compute icon under three different labels.
Speaker Notes: "Stress that a learner fluent in AWS is not starting over on Azure or GCP,
only relearning where things sit. Tie this to the shared-responsibility and security
foundations coming up, which apply the same way across all three consoles."
