Functions

Session 22 · 75 minutes · 28 cards · 24 beats · handout Task 1, Task 2

The one idea

A function is a named block written once. def only stores it; a call runs it, by jumping into the block and coming back. An argument sends a value in, and return hands a value back out.

By the end, a student can

  • Write a function with def, a name, brackets, a colon and an indented block.
  • Say why a function that is defined but never called prints nothing.
  • Follow a call: Python jumps to the block, runs it, then comes back to the line after the call.
  • Explain the NameError when a function is called before its def.
  • Pass a value with greet(word=name), and say why msg made inside is unknown outside.
  • Use return to get a value back, and say why a line after return never runs.

Comes after

21 - Lists and Strings

Notes for the team

  • The room is 50 to 60 first-year students on laptops. Laptops stay shut except on T1, T2 and the classroom quiz.
  • One world for the session: Teja's birthday. The deck's own input is Teja, so the hook, the tasks, the game and the exit are all at Teja's party. Friends: Rahul, Priya.
  • Votes are taken option by option: the instructor reads each option and asks how many think it is that one. Hands up. Nobody is named.
  • Calls are written only as greet(word=name), with the argument name and an equals sign, as the deck does. Never greet(name). That plain form is the next session.
  • One picture for the whole session: A call is drawn as a jump: an arrow from the call line up to the def header, and on the way back an arrow from the block to the call line. The call line stays marked while the block runs: it is waiting. A call opens the function's own area beside its block. Boxes made in the call (the argument, msg) live there, and vanish the moment the call ends. No grey ghost is left behind.
  • Nothing before the title card may say the session's name. The hook shows a song and a party, never code words like def.
  • The bar to beat is Plans/DSA/Module 3 - Stacks & Queues/01 - Introduction to Stacks/: a simulation the room drives, a picture that refuses to lie.

Fixed by pedagogy

The order of cards, what each card is for, the exact words a student reads, the code and its output, what happens on each press, and the must / must not lines.

Yours

Layout, visuals, colour, motion, the drawing of every object, and how each interaction is built. Every card has a Room to play line. Where the spec is silent, it is your call.

Rules for every card

  1. No autoplay. Nothing moves on a timer. One press, one move, with a caption that says what just happened.
  2. Commit, then reveal. Where a card asks a question, the answer shows only on the press after the room has answered.
  3. Wrong answers stay private. No names, no per-student results on screen. Hands are counted out loud, never shown.
  4. The topic is named once. Nothing before the title card says today's topic, not a heading, not a caption, not a file name on a code card.
  5. Words are exact. Words in quotation marks, and every line under Exact words, are final. The rest of a press describes what happens, in your own design. If an exact line does not fit, ask for a new one; do not rewrite it.
  6. Code is exact. Copy code and outputs from the JSON, never retype them. Every output here came from running the program.
  7. Simple English. Short sentences, everyday words. No em-dashes anywhere, the page title included.
  8. Every card moves. A card that introduces an idea steps; a static card is a picture of a lecture.

Build contract

  1. One self-contained HTML file. It opens offline from a USB stick and makes no network request.
  2. It opens in presenter view. There is no sidebar, top bar or button the instructor has to use.
  3. Right arrow or the clicker is one press. Left arrow goes back one press. F goes full screen, A shows all the cards, and End shows the whole card at once. The instructor guide tells the instructor these keys, so they must work.
  4. Every card is its own screen, in the order of this spec. Press 1 is what shows when the card opens.
  5. Every card's outer element carries data-spec="<card id>" and data-presses="<number of presses>". The review script reads both.
  6. No link to any other file. The students' handout and the instructor guide are separate files, and a link from this file is how a class finds the answers.

The JSON beside this file, 22_functions_session_spec.json, carries the same content with every program, output and trace as data. Build from it rather than copying out of this page.

Must

  • The verdict says why the answer is right, and gives a line for every wrong option.
  • Keys 1 to 4, or a click, may mark the room's choice. The right arrow works with or without a mark.
  • The answer appears on the object, not only as text.
  • Rounds 1 to 3 are Task 1's three runs in small form, so the machine checks the task.
  • A call is drawn as a jump: an arrow from the call line up to the def header, and on the way back an arrow from the block to the call line. The call line stays marked while the block runs: it is waiting.

  • An option is the TV screen itself: its lines one under the other. An error on the TV shows as its name, NameError; the step caption gives the full message.

  • Run anything on a timer. Movement inside one press is fine; a press that plays by itself is not.
  • Show the answer, a tick or a highlight on the right option before the steps run.
  • Show any one student's answer or result.
  • Show the code's output in a console before the object has moved.
